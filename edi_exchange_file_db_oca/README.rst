This module keeps the content of EDI exchange files in the database
instead of the filestore, so a database restored without its filestore
still holds every exchange payload. The **Exchange file** of an exchange
record is still an attachment: only the place where that attachment
keeps its content changes, from a filestore file to the database, so
everything that reads, writes or searches exchange files works as
before. It is enabled for every exchange type on installation, can be
disabled per type, and a size limit keeps big files in the filestore.
The exchange record form also shows the content of text files in a
**File Content** tab, with JSON indented.

Use Cases / Context
===================

Databases are often restored without their filestore for development,
debugging or testing: on a busy instance it can weigh far more than the
database, and copying it makes every restore slower and heavier. Such a
database keeps every exchange record but none of their files, so an
exchange can no longer be inspected, reprocessed or replayed to
reproduce an issue. EDI payloads are usually small and a negligible
share of the filestore, so keeping their content in the database costs
little.

Configuration
=============

No configuration is required: on installation every exchange type stores
the content of its files in the database.

To change it for one exchange type:

1. Go to *EDI > Config > Exchange types* and open the type.
2. Untick **Store File Content in Database** to keep the content of its
   files in the filestore, or set **Max File Content Size in Database
   (KB)** so that bigger files keep their content in the filestore. 0
   uses the global limit.

To set the global limit, go to *Settings > Technical > Parameters >
System Parameters* (developer mode) and edit
``edi_exchange_file_db_oca.max_size_kb``, in KB. The module creates it
with ``0``, which means no limit.

Both settings apply when a file is written: the files already stored
keep their content where it is (see **Usage**).

Usage
=====

Exchange files are handled as before: the module only changes where
their content is kept.

To read the content of an exchange file:

1. Go to *EDI > Exchanges* and open an exchange record.
2. Open the **File Content** tab. JSON is indented, and JSON and XML are
   highlighted; other text, such as CSV or EDIFACT, is shown as it is.
   Text that does not match the encoding of the exchange type is decoded
   with the encoding detected from its content.

Binary files, such as PDF, images or spreadsheets, and files above 1 MB
are not displayed: the tab shows their type, or their size limit, and
they are downloaded from the **Exchange file** field.

On installation, the content of the existing exchange files is moved
from the filestore to the database, following the type settings. Files
missing from the filestore, or whose content does not match their
checksum, are left untouched. The server log reports how many files were
moved and skipped. The moved filestore files are deleted by the regular
filestore garbage collection.

To move the existing files again later, for instance after enabling a
type or raising its limit, run from an Odoo shell:

.. code:: python

   from odoo.addons.edi_exchange_file_db_oca.hooks import (
       move_exchange_file_contents_to_db,
   )

   move_exchange_file_contents_to_db(env)
   env.cr.commit()

Uninstalling the module keeps every file readable, since Odoo reads the
content of an attachment from the database or from the filestore,
wherever it is; new files go to the filestore again. To move the stored
content back to the filestore as well, run
``env["ir.attachment"].force_storage()`` with the system parameter
``ir_attachment.location`` set to ``file``.

Development
===========

Odoo decides where an attachment keeps its content in
``ir.attachment._get_datas_related_values``, from ``_storage()``, which
knows neither the attachment's model nor its field. The decision is
therefore taken by the exchange record: ``edi.exchange.record`` writes
its **Exchange file** under the ``edi_exchange_file_content_in_db``
context key, for which ``ir.attachment._storage()`` returns ``db``.
Records are grouped by decision and each group is written with the key
set to ``True`` or ``False``, so a value inherited from the caller never
applies.

The key is scoped to the writing of the file only:

-  on creation, ``_create`` is overridden rather than ``create``, so the
   key covers the insertion of the rows and of their attachments, but
   not the quick execution of the exchange that ``edi_oca`` runs right
   after;
-  on update, ``write`` writes the other values first, then the file
   alone.

``edi.exchange.type._should_store_file_content_in_db(size)`` is the
single decision point: it combines the type's toggle with its size limit
(the type's own one, otherwise the global system parameter).

Content written to the attachment without going through the field, such
as ``ir.attachment.force_storage()``, follows the configured storage
instead.

``hooks.move_exchange_file_contents_to_db`` moves the existing content.
It selects the candidates in SQL, by batches, and asks their exchange
type. It reads each file, checks it against the stored checksum, and
writes the content with a batched SQL update: the checksum, size,
mimetype and index of the attachment stay valid since the content does
not change, and going through the ORM would recompute them for every
attachment.

The **File Content** tab decides between text and binary before
decoding: a file is binary when ``guess_mimetype`` recognises a binary
signature (PDF, images, Office documents, archives), or when its first
KB holds a NUL byte (except for UTF-16 and UTF-32 types). Decoding
success alone is not a reliable signal, since a type in ``latin-1``, or
with the ``replace`` error handler, decodes any byte sequence. The
display limit is ``_get_exchange_file_display_max_size()``.

Known issues / Roadmap
======================

-  A default on the backend, to configure every type of a backend at
   once.
-  From Odoo 19.0, writing an attachment with the database storage no
   longer marks its previous filestore file for garbage collection: the
   forward port must mark it itself.
-  A preview of PDF and image exchange files in the exchange record
   form.
